=== Contained Building Blocks

[cols="1,1,2",options="header"]
|===
| Bounded Context | Type | Responsibility

| Speaker
| Core
| Manages speaker profiles (name, biography, and later a picture). A profile has its own identity, separate from the account it belongs to, so one account can hold several role profiles.

| Talk
| Core
| Manages talks: a speaker creates, edits and deletes them independently of any conference. A talk records every conference it was submitted to, each submission freezing the talk's content at that moment.

| Conference
| Core
| Manages conferences, talk types, rooms, time slots, and the conference program. Receives talk submissions, decides whether to accept them, and schedules accepted talks. References talks by ID only.

| Voting
| Supporting
| Handles attendee ratings of talks (thumbs up / thumbs down). Designed for high throughput and independent scalability.

| Notification
| Supporting
| Delivers real-time notifications to attendees about conference program changes. Event-driven, asynchronous. Respects attendee opt-in preferences.

| Attendee
| Supporting
| Manages attendee registration, profiles, and preferences (e.g. notification opt-in).

| Content
| Supporting
| Handles upload and distribution of presentation slides. Speakers upload slides linked to their talks.

| Identity Provider
| Generic (external)
| Authentication and role management. Not a custom bounded context — addressed by a standard identity product. Other contexts integrate via an anti-corruption layer that translates tokens/claims into domain-specific roles.
|===

=== Important Interfaces

Bounded contexts communicate through well-defined interfaces. The following integration patterns are used:

* *ID references* — contexts reference entities from other contexts by ID only (e.g. `TalkId`, `AttendeeId`). No shared domain models.
* *Domain events* — contexts publish what happened and let others react. Talk publishes `TalkSubmittedToConferenceEvent`; Conference answers with `TalkSubmissionRegisteredEvent` or `TalkSubmissionRejectedEvent`, and later with `TalkAcceptedEvent` / `TalkRejectedEvent`. Notification subscribes to program changes from Conference.
* *Snapshots over synchronization* — a submission carries the talk's content, and the receiving conference stamps it with the speaker's details as they were at that moment. Neither is kept in sync afterwards: editing a talk or a profile affects future submissions only, so a conference always reviews and publishes what was actually submitted.
* *Local projections for identity and display* — a context keeps a minimal projection of another context's data where it needs it: Talk maps accounts to speaker profiles, Conference holds speaker names for submission snapshots. These are replicas fed by domain events, never a shared model or a synchronous call across the boundary.
* *Anti-corruption layer (ACL)* — contexts that interact with the external identity provider translate external claims into internal role/permission concepts.
