= Solution Strategy

== Domain-Driven Design

The system uses Domain-Driven Design. The problem space is divided into subdomains. Each subdomain maps to a bounded context in the solution space.

=== Subdomains

[cols="1,1,3",options="header"]
|===
| Subdomain | Type | Description

| Conference
| Core
| Manages conferences, rooms, time slots, and the conference program (scheduling).

| Talk
| Core
| Manages talks, speakers, abstracts, and tags. Speakers submit talks, and organizers review them. This happens before the talks go into the conference program.

| Voting
| Supporting
| Attendees rate how popular talks are (thumbs up or thumbs down). This subdomain has high traffic during a conference. It must scale independently.

| Notification
| Supporting
| Real-time notifications to attendees about changes to the conference program. Attendees must opt in.

| Attendee
| Supporting
| Attendee registration, profiles, and preferences (for example, the notification opt-in).

| Content
| Supporting
| Upload and distribution of presentation slides. Speakers upload slides for their talks. Attendees get the slides online.

| Identity
| Generic
| Authentication, authorization, and user and role management (speaker, organizer, attendee). A standard identity provider (for example, Keycloak, Auth0, or Entra ID) is the best solution for this subdomain. Do not develop a custom solution.
|===

=== Mapping Subdomains to Bounded Contexts

Not each subdomain needs a custom bounded context. The table shows how the subdomains map to bounded contexts in the solution space.

[cols="1,1,2",options="header"]
|===
| Subdomain | Bounded Context | Rationale

| Conference
| Conference
| Custom implementation. Core domain with conference-specific business rules.

| Talk
| Talk
| Custom implementation. Core domain with its own aggregate lifecycle (submit, review, accept).

| Voting
| Voting
| Custom implementation. It is separate because its traffic and scaling needs are very different (thousands of votes at the same time).

| Notification
| Notification
| Custom implementation. It is event-driven and delivers asynchronously. It has its own infrastructure needs (WebSocket, push).

| Attendee
| Attendee
| Custom implementation. It has the domain logic for attendees (registration, preferences).

| Content
| Content
| Custom implementation. It stores and distributes files. A CDN or an object store can support it.

| Identity
| _(no custom BC)_
| A standard identity provider does this task. An anti-corruption layer in the API changes the external identity tokens into domain-specific roles.
|===

== Modular Monolith

The system is a *modular monolith*. One ASP.NET Core application contains all bounded contexts. Each bounded context is a separate module with clear boundaries.

* *Single API*: One ASP.NET Core host shows all endpoints. Each module registers its own controllers and endpoints. Externally, there is one API.
* *Event store per module*: Each module saves its aggregate state as an immutable sequence of domain events. It uses `IEventStore` for this. A module must not access the event stream of another module directly. The persistence technology behind `IEventStore` is not decided (see open decision OD-3). The current implementation uses an in-memory event store as a placeholder.
* *In-process communication*: Modules communicate through defined interfaces (domain events, mediator, or explicit contracts). They do not use network calls.
* *Extractability*: The strict module boundaries let you move a bounded context into a separate service later. This is necessary if scaling or organizational needs change.

== Clean Architecture

Each custom bounded context has the layers of Clean Architecture:

....
API  ──►  Application  ──►  Domain
 │                            ▲
 └──────►  Persistence  ──────┘
....

* *Domain*: Aggregates, entities, value objects, and domain events. It does not depend on other layers.
* *Application*: Use cases (commands and queries). It depends only on the domain. It does not know the Persistence layer.
* *Persistence*: The repository implementations for the bounded context. The repositories load and save aggregate state as domain events. They use the `IEventStore` interface of the shared infrastructure. It depends on the domain.
* *API*: The ASP.NET Core entry point, the dependency injection, and the HTTP endpoints. It depends on all other layers.
